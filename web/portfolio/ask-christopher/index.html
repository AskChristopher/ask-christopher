01 The problem

Visitors arrive with questions, not time

A portfolio site makes every visitor do the same work: read pages until they find the answer to their own question. A hiring manager wants to know whether I've built scenario-based learning. A small-business owner wants to know whether their problem even needs a course.

That's a performance-support problem, so I treated it like one: put the answer where the question happens.

02 The constraints

It speaks for a real person

  • No invented claims. An assistant that represents me can't fabricate a credential, a project or a client. That was a launch-blocking rule, not a nice-to-have.
  • Honest about evidence. Some work is public, some is private for a reason, and some isn't written up yet. The assistant has to say which.
  • Small budget, simple hosting. Shared hosting, Python 3.11, manual deploys, and every live test costs real money.
03 The thinking

Curate the knowledge, then test the behavior

Write the knowledge like content, not data. Six hand-written files (bio, philosophy, projects, services, FAQ, boundaries), each project entry explaining why it exists and what I learned, not just what it is.

Start simple, measure, then decide. The whole knowledge base, about 24,000 tokens, goes into every request and is served from the prompt cache. I recorded that as a baseline decision with a stated point at which it gets revisited, instead of building retrieval before it was needed.

Treat honesty as something you test. Status and evidence each have their own vocabulary (built, in progress, planned; public, private for a reason, described only), so "is this real?" has a precise answer.

04 The system

Five parts, one prefix

  1. 01Knowledge

    Six curated Markdown files.

  2. 02Behavior

    Persona, teaching style, grounding rules.

  3. 03Assembly

    A byte-identical prefix, so caching holds.

  4. 04Model

    Claude via the Anthropic API.

  5. 05Interface

    Conversation plus a showcase of related work.

Behind it is an evaluation harness that scores answers three different ways and never mixes the results: automatic checks that can catch a failure but never confirm a pass, a three-lens model judge that must quote the answer verbatim to fail it, and human review for the cases only a person should grade.

Ask Christopher has been this site's homepage since August 29, 2026. Live use also exposed a bug the tests didn't cover: after a long answer, the visitor's follow-up question was rejected, because a length limit meant for questions was being applied to the assistant's own previous reply. It was traced, fixed, and confirmed in production on September 3.

06 What I learned

Small overclaims are the real risk

The failures weren't hallucinations. The findings that remain are single sentences that stretch slightly past the evidence, like implying all my projects are documented on GitHub when two of seven were. Those are the claims a visitor is most likely to check.

An assistant only knows what you give it. When I published my first case study, the assistant couldn't mention it, because its knowledge still described only my code repositories. The portfolio pages and the assistant's knowledge now live in the same repository and ship together.

Test the path people actually use. Single questions passed; real conversations broke. The follow-up after a long answer is where the bug lived.
